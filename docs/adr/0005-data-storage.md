# ADR-0005: Хранение рыночных данных и состояния

**Статус:** Принято
**Дата:** 2026-07-11

## Контекст

Три разных по природе класса данных:

1. **Сырой поток бирж** — большой объём, append-only, нужен для replay (ADR-0004)
2. **Горячее состояние** — текущие книги, позиции, последние цены, флаги kill switch; читается на каждом тике
3. **Аудит и учёт** — ордера, fills, позиции, решения риск-движка, PnL; нужна транзакционность и запросы

Тик-аналитика (SQL по миллиардам строк) в v1 не требуется — исследования идут по capture-файлам.

## Решение

### Фаза 1 (v1)

| Класс данных | Хранилище |
|---|---|
| Сырой WS/REST capture | **JSONL-файлы** на диске (ротация по часу + gzip), один файл на venue/день |
| Горячее состояние | **Redis**: книги (top-N уровней), позиции, last-known цены, runtime-флаги |
| Ордера, fills, позиции, аудит, конфиг стратегий | **Postgres** (транзакционный журнал, единый источник истины по учёту) |

- Capture-файлы — канонический источник для replay/backtest; формат: `{ts_recv_ns, venue, channel, payload}`
- Схема Postgres версионируется миграциями (node-pg-migrate)
- Redis без persistence-критичности: состояние восстанавливается из Postgres + ресинхронизации книг при рестарте

### Фаза 2 (при необходимости)

Тик-данные в **TimescaleDB** (hypertables поверх уже работающего Postgres) или **QuestDB** — решение отдельным ADR, когда capture-файлы перестанут хватать для исследований.

## Последствия

- Минимум инфраструктуры на старте: Redis + Postgres + файловая система — запускается одним docker-compose
- JSONL-capture прост, читаем и надёжен; минус — объём (смягчается ротацией/сжатием и выгрузкой в S3/parquet скриптом)
- Postgres как единый источник истины по ордерам/fills исключает расхождения «что мы реально купили» между модулями
- Отложенный выбор time-series БД не блокирует v1: replay работает с файлов с первого дня
