# Создание ADR

Зафиксируй архитектурное решение: $title

## Когда нужен ADR

Создавай ADR при решениях, которые дорого/больно менять или которые должны соблюдаться всем кодом: стек, коннекторы, хранилища, риск-политики, границы модулей, изменение scope, отмена прежних решений. Мелкие рефакторинги ADR не требуют.

## Шаги

1. Найди следующий номер: посмотри индекс в `docs/adr/README.md` и файлы `docs/adr/*.md` (формат `NNNN-kebab-title.md`, ведущие нули)
2. Создай файл `docs/adr/NNNN-kebab-title.md` по шаблону ниже
3. Статус нового ADR — `Предложено`; `Принято` — после подтверждения пользователем
4. Добавь строку в таблицу индекса `docs/adr/README.md`
5. Если ADR отменяет старое решение: в старом файле статус → `Заменён` со ссылкой на новый ADR

## Шаблон

```markdown
# ADR-NNNN: <Название решения>

**Статус:** Предложено
**Дата:** YYYY-MM-DD

## Контекст

<Почему решение нужно: проблема, ограничения, рассмотренные альтернативы с плюсами/минусами>

## Решение

<Что именно решено — конкретно и проверяемо>

## Последствия

<Что это даёт, чем жертвуем, что теперь запрещено/обязательно, влияние на другие ADR>
```

## Правила

- Один ADR = одно решение (не смешивать стек и хранилище в один файл)
- Проза на русском; термины, идентификаторы, URL, код — на английском
- Принятый ADR по смыслу не редактируется: изменение решения = новый ADR со статусом `Заменяет ADR-XXXX`, а старый → `Заменён`
- Решение должно быть проверяемым: «используем pnpm workspaces», а не «хорошая структура проекта»
- Если решение меняет правила из `AGENTS.md` — обнови и его
